# Универсальная инструкция по UI/UX для продуктового интерфейса

Этот документ можно перенести в другой проект и использовать как руководство для команды или контекст для AI-агента. Он подходит для рабочих приложений: CRM, редакторов, карт, систем управления, мониторинга и аналитики. Конкретная структура определяется задачами пользователей.

## 1. Контекст продукта

Перед проектированием заполните:

- **Продукт:** что делает приложение.
- **Аудитория:** кто им пользуется и насколько знаком с предметной областью.
- **Основные задачи:** 3–5 результатов, которых пользователь хочет достичь.
- **Объекты:** с чем работает пользователь — проекты, документы, заявки, устройства и т. п.
- **Частота:** эпизодическое или ежедневное использование.
- **Устройства и языки:** поддерживаемые размеры экрана, способы ввода, локализация.
- **Ограничения:** существующие компоненты, бренд, права доступа, технический стек.

Для каждого основного сценария опишите: точку входа → выбор → действие → результат → исправление ошибки. Сначала определяйте поведение и структуру, затем визуальное оформление.

## 2. Структура рабочего пространства

Полезная модель для приложений с объектами:

**Найти объект → выбрать → посмотреть детали → выполнить действие → увидеть результат.**

Возможное распределение областей:

| Область | Назначение |
| --- | --- |
| Основная навигация | Переход между разделами продукта |
| Список или дерево | Поиск, фильтрация и выбор объектов |
| Центральная область | Основная работа: документ, таблица, карта, редактор |
| Инспектор | Детали и команды выбранного объекта |
| Панель инструментов | Частые команды текущего контекста |
| Дополнительная панель | Второстепенная задача без потери контекста |

Не все области нужны каждому продукту. У каждой видимой панели должна быть понятная роль. Держите частые действия рядом с их объектом; второстепенные подробности раскрывайте постепенно.

## 3. Навигация

### Разделяйте разные виды взаимодействий

| Намерение пользователя | Элемент |
| --- | --- |
| Перейти на страницу или в раздел | Ссылка |
| Выполнить команду | Кнопка |
| Выбрать объект в текущем рабочем пространстве | Кнопка выбора с обозначенным состоянием |
| Раскрыть дочерние пункты | Кнопка раскрытия |
| Переключить соседние представления одного контекста | Вкладки |
| Открыть дополнительные команды | Кнопка меню |

- Группируйте разделы по пользовательским задачам и понятным сущностям.
- Используйте конкретные названия: «Документы», «Участники», «Настройки проекта».
- Название меню должно объяснять его содержимое. Не смешивайте управление проектом, настройки вида и помощь без явной группировки.
- Частые задачи не должны требовать нескольких последовательных подменю. Глубокую иерархию дополняйте поиском и отдельными страницами разделов.
- Различайте текущий раздел, выбранный объект, раскрытую группу и клавиатурный фокус.
- При многоуровневой структуре показывайте положение пользователя: заголовок, выбранный пункт, при необходимости хлебные крошки.
- Сохраняйте фильтры, прокрутку и выбор при возврате, если это помогает продолжить работу.
- Определите поведение Back/Forward, обновления страницы, прямых ссылок и новых вкладок.
- Состояние, которым нужно делиться, отражайте в URL. Черновики и чувствительные данные требуют отдельной стратегии хранения.
- Открытие в новой вкладке делайте осознанно и обозначайте пользователю.

## 4. Вложенные пункты и дополнительные кнопки

### Иерархия разделов

Для структуры «Проекты → Проект → Документы» используйте раскрываемые группы или переход на страницу проекта. Если название открывает страницу, а стрелка раскрывает дочерние пункты, это должны быть разные зоны нажатия.

### Действия у строки

Пример: название проекта открывает проект, стрелка раскрывает дочерние элементы, кнопка `…` открывает команды этого проекта.

- Не вкладывайте `<button>` в `<button>`, ссылку в ссылку или кнопку внутрь ссылки.
- Размещайте самостоятельные интерактивные элементы соседями в общем контейнере строки.
- У каждого элемента должна быть одна предсказуемая функция и доступное имя.
- Нажатие на `…` не должно одновременно выбирать объект или выполнять переход.
- `stopPropagation()` может управлять событиями, но не исправляет некорректную HTML-структуру.
- Основное действие оставляйте доступным напрямую. В `…` переносите редкие команды.
- Не делайте hover единственным способом обнаружить или выполнить действие. Поддерживайте клавиатуру и сенсорный ввод.
- У иконки меню указывайте контекст: «Действия с проектом Альфа».
- Используйте `aria-expanded` для раскрытия; для текущей страницы — `aria-current="page"`. Остальные состояния обозначайте согласно семантике выбранного компонента.
- После закрытия меню возвращайте фокус к его кнопке. После удаления строки переводите фокус в логичное доступное место.
- Escape закрывает верхний активный слой или отменяет текущий режим, не вызывая побочные команды в нижележащем интерфейсе.

В shadcn/ui для строки с действием предусмотрены соседние `SidebarMenuButton` и `SidebarMenuAction`, для дочерних пунктов — `SidebarMenuSub`. Сверяйте API с установленной версией и локальным исходным кодом.

## 5. shadcn/ui и система компонентов

shadcn/ui предоставляет исходный код компонентов, который добавляется в проект и может адаптироваться командой. Это основа собственной библиотеки интерфейса. Информационную архитектуру, состав меню и пользовательские сценарии нужно проектировать отдельно.

Перед использованием изучите `package.json`, `components.json`, локальные компоненты и глобальные стили. Проверьте используемую основу компонентов: например, Radix UI или Base UI. Не смешивайте их API по памяти.

### Выбор компонента

| Задача | Компонент или подход |
| --- | --- |
| Навигация приложения | Sidebar и ссылки |
| Второстепенные команды | DropdownMenu |
| Независимая настройка вкл./выкл. | Switch или Checkbox |
| Выбор одного варианта | RadioGroup, Select, Combobox |
| Переключение представлений | Tabs |
| Короткая отдельная задача | Dialog |
| Подтверждение значимого опасного действия | AlertDialog |
| Дополнительная панель | Sheet или Drawer по задачам продукта |
| Второстепенные подробности | Accordion |
| Дополнительное пояснение | Tooltip |
| Краткое уведомление | Toast или принятый в проекте аналог |

- Используйте общие токены цветов, отступов, типографики, радиусов и размеров элементов.
- Предпочитайте семантические цвета: фон, текст, граница, ошибка, выделение.
- Определите общие варианты кнопок: основная, вторичная, малозаметная, опасная.
- Не создавайте новую стилизацию одного и того же элемента на каждом экране.
- Проверяйте, какой HTML создают композиция, `asChild` и обёртки: одна видимая кнопка должна оставаться одним интерактивным элементом.
- Сохраняйте поведение клавиатуры и управление фокусом при кастомизации.
- Проверяйте доступность готовой композиции. Доступные примитивы не гарантируют доступность всего экрана.
- Учитывайте сопровождение: изменения локального кода компонентов и обновления исходных шаблонов нужно согласовывать.

## 6. Состояния и обратная связь

Для каждого сценария предусмотрите применимые состояния:

- первоначальная и повторная загрузка;
- отсутствие данных и отсутствие результатов поиска;
- отсутствие доступа;
- ошибка ввода и ошибка операции;
- выполнение, успех и повторная попытка;
- недоступность действия с понятной причиной;
- отмена и восстановление после ошибки пользователя.

Пустое состояние объясняет ситуацию и предлагает следующий шаг: создать объект, очистить поиск, сменить фильтр. Недоступная команда объясняет условие её доступности. Не полагайтесь только на `title`: его трудно обнаружить с клавиатуры и на сенсорном экране.

Не показывайте успех до подтверждения операции, если нет продуманного оптимистичного обновления с откатом. Существенные ошибки и инструкции не должны исчезать только потому, что истёк таймер уведомления.

Для обратимых действий предпочтительна доступная отмена. Для существенных необратимых последствий нужно осознанное подтверждение с описанием результата. При смене контекста учитывайте несохранённую работу.

Разделяйте состояние просмотра и состояние редактирования: например, фильтр списка не должен неожиданно менять параметры создаваемого объекта.

## 7. Мобильный интерфейс и доступность

- Адаптируйте последовательность работы: список → объект → детали. Несколько одновременных панелей на телефоне часто удобнее заменить последовательными представлениями.
- Сохраняйте основные функции и доступ к полной информации при сокращении подписей.
- Для частых сенсорных действий ориентируйтесь на области около 44×44 CSS px. Это рекомендация для удобства, а не универсальная формулировка минимума WCAG.
- Используйте читаемые размеры текста; мелкие подписи проверяйте на реальном устройстве.
- Обеспечьте работу с клавиатуры, логичный порядок Tab и заметный фокус.
- Не передавайте статус только цветом: добавьте текст, форму или иконку.
- Поля должны иметь постоянные подписи; placeholder не заменяет label.
- Учитывайте длинные названия, переводы, масштабирование текста и reduced motion.
- Проверяйте экранную клавиатуру, безопасные области экрана, небольшую высоту окна и доступность кнопок закрытия.
- Горячие клавиши не должны срабатывать во время ввода текста или конфликтовать с открытым меню и диалогом.

## 8. Скиллы

Скиллы ниже зависят от окружения агента. Перед использованием проверьте их наличие и прочитайте соответствующий `SKILL.md`. Перенос этого документа сам по себе не устанавливает скиллы.

| Скилл | Когда использовать |
| --- | --- |
| `astra-frontend-design` | Проектирование экранов, визуальная иерархия, плотность, адаптация, UX-аудит и визуальная проверка |
| `frontend-ui-engineering` | Реализация компонентов, семантика, доступность, клавиатура, состояния, адаптивная вёрстка |
| `figma:figma-design-to-code` | Реализация интерфейса по дизайну Figma |
| `figma:figma-generate-design` | Создание или обновление составных экранов в Figma |
| `code-simplification` | Упрощение работающего кода без изменения поведения |
| `skill-creator` | Создание отдельного переиспользуемого скилла с правилами команды |

Базовая связка для продуктового интерфейса: **`astra-frontend-design` + `frontend-ui-engineering`**. Figma-скиллы подключайте при работе с Figma, упрощение кода — по необходимости. Если скилл отсутствует, явно сообщите об этом и согласуйте подходящую замену, когда отсутствие мешает задаче.

## 9. Проверка качества

Проверяйте основной сценарий целиком, включая ошибки и возврат к работе.

- Представительные ширины: 320, 768, 1024 и 1440 px; дополнительно небольшая высота окна.
- Навигация, выбранное состояние, раскрытие групп и дополнительные действия.
- Клавиатура, Escape, порядок фокуса, вход в диалог и возврат после закрытия.
- Сохранение фильтров, выбора и черновиков при переходах.
- Back/Forward, обновление страницы и прямые ссылки.
- Загрузка, пустые состояния, ошибки, недоступные команды и восстановление.
- Длинные тексты, локализация, масштабирование, светлая и тёмная темы при их наличии.
- Отсутствие перекрытий, случайных двойных действий и непредусмотренной горизонтальной прокрутки.

Используйте существующие инструменты проекта. Для реализации запускайте проверки, соответствующие изменению, и осматривайте реальные скриншоты. Успешная сборка не заменяет проверку интерфейса. В отчёте разделяйте подтверждённые дефекты, выводы по коду и гипотезы, требующие проверки с пользователями.

## 10. Готовый промпт для другого проекта

```text
Используй $astra-frontend-design и $frontend-ui-engineering,
если они доступны. Прочитай правила репозитория и соответствующие
SKILL.md. Проверь актуальную документацию установленного стека.

Контекст:
— Продукт: [описание].
— Аудитория: [роли и опыт].
— Главные задачи: [3–5 задач].
— Основные объекты: [список].
— Частота использования: [описание].
— Устройства и языки: [список].
— Ограничения и дизайн-система: [описание].
— Режим работы: [аудит / проектирование / реализация].

Используй UI-UX-GUIDE.md как руководство, адаптируя рекомендации
к продукту. Не предполагай, что все перечисленные панели нужны.

1. Изучи существующие экраны, компоненты, стили и поведение.
2. Опиши основные сценарии и структуру навигации.
3. Раздели переходы, выбор объектов, раскрытие и команды.
4. Спроектируй строки с дополнительными действиями без вложенных
   интерактивных элементов и случайных двойных срабатываний.
5. Используй существующие компоненты и токены; при shadcn/ui
   проверь локальную реализацию и совместимость API.
6. Учти состояния, причины недоступности, ошибки и восстановление.
7. Определи сохранение контекста, URL и поведение Back/Forward.
8. Адаптируй основные сценарии под телефон и клавиатуру.
9. При реализации проверь рабочий сценарий в браузере на широком
   и узком экране, осмотри скриншоты и исправь существенные дефекты.

Результат: логика интерфейса, структура навигации, основные
сценарии и состояния, правила компонентов, результаты проверки
и оставшиеся ограничения.

При аудите не меняй файлы. При реализации доведи запрошенный
сценарий до работающего и проверенного результата.
Не выдавай предположения по коду за результаты браузерной проверки.
```
